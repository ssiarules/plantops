PlantOps real backend: where data lives, how the agent knows the building

Demo today is sample only. Real version swaps the sample file for real adapters, same flow, same approval gate. Sample data only in the submission, architecture only.

Demo today, where data actually comes from

Manager message in Switch room→PlantOps agent, Claude Code, working directory is plantops-agent repo→Local Python tools: plantops/data.py, triage.py, work_order.py, worker.py→Hardcoded sample register: S-01 to S-05, S-02 Lobby planter B, Zone B, sample weather hot and dry, sample irrigation low flow, sample care log→Proposal, Approve, log in local JSON state file

Switch does NOT provide plant, weather, or irrigation data. Switch is the chat transport. The agent provides the data, by running tools. In the demo, those tools read a sample file. That is why the demo is basic, and why it is safe to submit.

How the agent knows which building, which plant, which floor

  1. Room equals building. One Switch room per building, not one room for everything. Room metadata maps room_id to building_id. When a message arrives from Planters Building 1 room, the agent knows building_id for that room, without asking the manager.
  2. Plant row carries the rest. A plant is not just a name. Its row is: building_id, floor, room or office, planter, zone, type, condition, last care, next care. Example, real shape, sample values only: building Sample Building 1, floor Lobby, planter B, plant S-02, zone B. In a real building, floor would be 7, 8, roof, and so on, from the register, not from chat text.
  3. Triage joins the sources. Agent queries register for that building, weather for that building location, irrigation for that zone, care log for that plant, then proposes one prioritized work order. If any source is missing, agent says so plainly, and does not invent it.
  4. Approval is the gate. No irrigation change, no vendor dispatch, no payment, until Manager replies Approve in that building room. After Approve, agent writes the work order to the database, posts the worker checklist, and only then can a gated control tool run, with the work order id in the audit log.

Does the agent have access to tools outside Switch? Yes, that is the point.

Switch ships no agents and no models, and it does not replace the chat app. It connects an existing agent to a team chat. The agent itself can use tools outside Switch, through:

  • Switch Agent Protocol, the connection between agent harness and Switch room.
  • MCP servers, for database, files, APIs, and other tools, exposed to the agent harness.
  • HTTP APIs, with keys held by the agent host, never posted in chat, never in the repo, per building and per vendor, read only first.
  • CLI tools in the agent working directory, like the demo Python tools, replaced in real life by database and API adapters with the same function names.

Switch is one source of communication, not the only source of data. Chat is where people decide. Database, weather, irrigation, and photos are where data lives. The agent is the bridge between them, and the approval gate is what keeps that bridge safe.

What I recommend, for the hackathon and after

  1. For Nov 7 submission, keep the demo sample only. Track 01 asks for a workflow in a team chat where a person and an agent get a real task done, with Switch central, and a README that shows how Switch was used. The basic demo already does that, with a real approval gate, a real log, and a real worker checklist. Adding live weather, live irrigation, or live database keys before Nov 7 risks keys in the repo, real building data in a public submission, and a broken demo on judging day.
  2. Add this architecture diagram and a Real world section to the README, not live integrations. Judges see the path to real, without you shipping keys or real data. State plainly: demo data is sample, real adapters swap in place of data.py, same flow, same gate.
  3. After the hackathon, build real integrations one at a time, in this order: (1) Supabase or Postgres register, buildings, floors, plants, care log, work orders, with room to building mapping. (2) Weather API, read only, by building location. (3) Irrigation API, read only first, zone status and faults. (4) Irrigation control, gated, only after Manager Approve, with audit log. (5) Photo storage linked to work order, not just room attachment. Each step gets its own test and its own go, same Architect, Direct, Audit, Deploy loop.
  4. Privacy gate for any real building: a real building deployment needs owner and manager approval, per building permissions, and sample data only in any public demo. A real pilot building is inspiration and proof of the pattern, not demo data, and not a public case study, without explicit go from the people who own and manage it.
